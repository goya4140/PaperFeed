# PaperFeed 产品化工程方案

整理日期：2026-10-13。根据产品讨论归档；以下是下一阶段建议，不代表已经实现、上线或完成技术选型。

需求更新：2026-10-20。当前产品名称使用 PaperPop。每篇论文直接交流、研究方向社区、结构化论文 Poster 为本轮核心需求；详细 checklist 和确认/建议边界见 [当前需求更新](paperfeed_product_overview_v0.1.md#当前需求更新--2026-10-20)。

## 产品定位与工程目标

让研究者轻松理解前沿研究、发现兴趣内容、连接同方向同行。重点是交流、兴趣与热点：每篇研究内容及领域社区中的讨论，兴趣驱动的推送，以及优秀实验室和公司的论文、官方博客、技术报告和项目进展。

轻松理解是核心价值：以标准化论文 Poster 为主要入口，呈现研究问题、方法图解、关键结果、原文证据、实验条件和局限，适配手机分模块浏览。每篇论文可直接讨论，研究方向社区支持问题、回答及讨论帖。刷到研究 → 看懂 Poster → 表达兴趣 → 论文讨论/方向交流 → 收藏、深读与使用。音频和视频降为后续可选能力。

iOS 与 Web 共享内容、账号、推荐与社区服务。当前 Sites Demo 保留作为体验与展示基础。

## 参考项目：已知事实与未知部分

- [papers.cool 官方仓库](https://github.com/bojone/papers.cool)：主要是更新日志、反馈入口与扩展，并未提供完整后端源码。公开日志提到本地历史论文库、Tantivy/BM25 搜索、PDF 文本抽取和 Kimi 解读排队。可借鉴其数据、搜索、生成与阅读界面的分离。
- [arXivDaily](https://www.arxivdaily.com/)：公开页面展示每日内容、分类、AI 总结、翻译、机构检索和纠错入口。内部数据库、队列和部署方式尚未确认，不能把推测当成实现事实。

## 每日内容处理链路

官方来源 → 定时增量采集 → 去重及版本识别 → 元数据入库 → 方向识别和候选筛选 → 异步生成 → 证据检查及编辑审核 → 发布和搜索索引 → 推荐 API → iOS/Web。

阅读、收藏、正负反馈和讨论事件回流到推荐服务。基础解读共享复用，个性化主要体现在候选、排序和推荐理由。

- 保存采集进度、支持断点续跑、重叠窗口补漏与历史回填。
- 同一论文跨分类收录去重；区分论文实体与版本；关联官方博客和论文以减少重复推荐。
- 区分首次提交、论文版本更新、发现时间及解读发布时间。
- 每篇内容独立任务，处理超时、限流和重试；幂等键防止重复内容及重复通知。
- 原文更新后检查是否需要修订解读，保留生成与审核版本以及纠错记录。
- 每个来源独立适配，记录采集覆盖、最近成功时间与异常。

arXiv 官方建议 OAI-PMH 用于批量元数据同步，搜索 API 用于查询，RSS 可辅助每日发现。OAI-PMH datestamp 是元数据修改时间，不等于首次提交时间。核验时的旧接口规则是整体每三秒最多一次请求、单连接；实施前再次核对规则。

来源：[批量访问](https://info.arxiv.org/help/bulk_data.html)、[OAI-PMH](https://info.arxiv.org/help/oa/index.html)、[API 使用规则](https://info.arxiv.org/help/api/tou.html)。

## 分层内容生产

| 层级 | 范围 | 产物 |
| --- | --- | --- |
| 发现 | 选定方向的新内容 | 元数据、摘要、分类和原文入口 |
| 速读 | 以每篇收录论文为覆盖目标，分批生成 | 标准化 Poster：问题、方法、图解、结果、条件、局限、证据和讨论入口 |
| 精品 | 少量重要或高需求内容 | 全文深读、扩展图解和共读专题；音频/视频后续可选 |

不要为每篇论文都制作视频，也不要为每个用户重复生成同一篇解读。完整深读需要读取原文，仅靠摘要扩写不足以支撑证据。

生产步骤：读取原文 → 提取带出处的证据 → 按论文类型填充 Poster 模板 → 生成结构化模块及图表 → 检查事实、实验条件和手机可读性 → 审核发布。未生成或失败时展示真实状态及摘要/原文入口。

paper2poster 类开源框架列为待评估路径，尚未选型或接入。评估输出质量、中文、移动端呈现、结构化产物、部署成本与许可证；通过独立适配层连接生成流程，客户端不绑定某个框架的图片输出格式。

每条成品记录论文版本、证据位置、模型、模板版本、审核状态和成本；低质量结果退回重做。外部全文和博客是资料，不是模型的工具调用指令。

元数据、原创解读、原文链接与授权媒体分别管理。全文及原图存储和分发需检查实际许可，不将公开可读理解为可以重新托管。

## 当前基础与缺口

| 能力 | 当前基础 | 下一步 |
| --- | --- | --- |
| 采集 | 固定内容写在 lib/papers.ts | 来源配置、增量任务、版本、补漏 |
| 生产 | 固定深读、分镜及本机 macOS 配音脚本 | Poster 模板与结构化产物、框架评估、云端队列、证据、质量门槛和成本预算 |
| 运营 | 修改源码发布内容 | 后台批量审核、重做、纠错、上下架 |
| 数据 | 论文在源码，研究空间以 JSON 保存在 D1 | 论文、版本、解读、媒体、用户、收藏、讨论等独立记录 |
| 身份 | Sites 身份或匿名演示空间 | 面向双端的账号、权限、跨设备同步 |
| 社区 | 自己的操作真实保存，人物和历史互动为示例 | 每篇论文的共享讨论、方向社区、问题/回答/评论关联、站内通知和运营处理 |
| 推荐搜索 | 小内容集的可解释规则 | 服务端召回排序、搜索索引、事件和效果评估 |
| 运维 | 类型、构建及功能检查 | 环境隔离、CI/CD、备份恢复、监控告警 |

后台需看见每批采集数量、来源覆盖、失败任务、待审核内容、生成成本和纠错状态。

## iOS 与 Web 架构建议

先建立按模块组织的统一后端 API，加异步任务队列、数据库与媒体存储，不急于拆分大量微服务。D1 是否迁移由实际查询、并发和运营需求决定，尚未选定最终数据库与任务运行平台。

iOS 需处理 Poster 分模块阅读与图表放大、阅读位置恢复、离线阅读、推送、深链接、弱网同步、崩溃监控和客户端版本兼容。音频中断在后续启用音频功能时处理。不要只将网页包装为 App。

真实社区上线需内容过滤、举报、屏蔽及运营处理。支持账号创建时，提供应用内发起删除账号的入口。具体上架要求在实施时重新核对。

来源：[Apple 审核规则](https://developer.apple.com/app-store/review/guidelines/)、[账号删除](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)。

## 下一阶段里程碑与验收

先选几个相互关联的研究方向和少量官方来源，建立可连续运行的内容后台。

1. 自动发现新论文与版本更新，重复运行无重复记录。
2. 批量生成标准化 Poster，验证证据准确性、手机可读性及生成状态；精选内容进入深读生产。
3. 编辑无需改源码即可审核、纠错、重做和发布。
4. 发布后 Web 自动显示，同一 API 能供 iOS 使用。
5. 连续运行一周，能够追踪采集覆盖、失败任务、内容延迟及单篇成本。
6. 两个独立账号完成同一论文下提问、回复、站内通知与直达；无需先加入社区。
7. 完成方向社区发帖、问题回答、论文关联及内容管理，验证论文与社区间的双向访问。

此计划尚未实施；当前已实现功能、测试与真实边界见 implementation-status.md 和 README.md。
